# ADR-006: Transaction Propagation via Closure TxManager with Ambient Context Executor

## Status
Accepted (2026-09-21)

## Context
Multi-step business operations—such as orphan-safe member deletion, Excel tree import, and identity resolution—require strict atomicity across multiple repository operations. Passing raw database transaction pointers (`*pgx.Tx`) through service interfaces pollutes domain APIs with database driver specifics and complicates unit testing. Conversely, manual transaction handling across nested services risks unhandled panics, leaking open transactions, and silent rollbacks.

## Decision
1. **Closure-Style Transaction Runner**:
   - Provide `TxManager.WithTx(ctx, fn)` as the standard transaction propagation primitive.
   - `WithTx` begins a transaction, injects it into an ambient context key (`txCtx`), defers automatic rollback on error or panic recovery, and commits only on `nil` return.
2. **Ambient Context Executor Resolution**:
   - Repositories call `database.GetExecutor(ctx, pool)` to obtain a `DBTX` interface. If an ambient transaction is present in `ctx`, it is returned; otherwise, the default connection pool is used.
3. **Fail-Fast Nested Transactions**:
   - Calling `WithTx` inside an already active `WithTx` context returns an explicit error (`nested transactions are not supported`). Savepoints are deferred until a proven requirement emerges.
4. **Service-Level Transient Retry Policy**:
   - Serialization failures (`40001`), deadlocks (`40P01`), and race condition unique violations (`23505`) on concurrent first-time logins are intercepted and retried up to 3 times with exponential backoff and jitter (50ms $\times 2^n \pm \text{jitter}$). Permanent business violations (`23503`, 409 conflict) fail immediately.

## Consequences
- **Positive**: Domain and service layers remain 100% free of database driver imports.
- **Positive**: Standardized, fail-safe error handling and panic recovery across all mutating database workflows.
- **Negative**: Ambient context propagation is opaque to static analysis, requiring disciplined use of `GetExecutor`.
