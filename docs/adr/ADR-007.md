# ADR-007: Concurrency Contract & Lock Ordering for Identity Management

## Status
Accepted (2026-09-21)

## Context
Concurrent authentication requests (such as simultaneous callbacks from two OAuth tabs, or rapid double-clicking of email magic link tokens) can cause race conditions. Issues include duplicate user rows, unique constraint violations on `contact_points(kind, value)`, and race windows during account unlinking that could delete a user's final identity despite protection checks. A predictable concurrency and locking protocol is essential.

## Decision
1. **READ COMMITTED with Explicit Advisory Locks**:
   - First-time login and contact point creation acquire a PostgreSQL transaction advisory lock on the hashed contact value: `SELECT pg_advisory_xact_lock(hashtext(kind || ':' || value))`.
   - Any concurrent attempt waits for the initial transaction to commit. If a unique violation (`23505`) still occurs on insert, the transaction rolls back and re-resolves the login as an auto-link.
2. **Canonical Parent-Row Locking for Identity Mutations**:
   - To guard against deleting the last remaining identity, the transaction executes:
     `SELECT id FROM users WHERE id = $1 FOR UPDATE`.
   - It then counts `user_identities`. If count $\le 1$, the operation aborts with `409 Conflict` before performing any deletion.
3. **Atomic Single-Use Token Consumption**:
   - Magic link tokens are consumed in a single atomic SQL statement:
     `UPDATE magic_link_tokens SET consumed_at = NOW() WHERE token_hash = $1 AND consumed_at IS NULL AND expires_at > NOW() RETURNING email`.
   - Replay attempts fail immediately with `401 Unauthorized`.
4. **Global Lock Ordering Discipline**:
   - To eliminate distributed deadlocks, all multi-table transactions acquire locks in strict hierarchy:
     $\text{Advisory locks} \rightarrow \text{users (id ASC)} \rightarrow \text{user\_identities / contact\_points} \rightarrow \text{families} \rightarrow \text{members (id ASC)} \rightarrow \text{parent\_child / spouses} \rightarrow \text{feed\_posts / outbox\_events}$.
5. **Zero External I/O Inside Transactions**:
   - External OAuth HTTP requests and SMTP email transmissions are strictly forbidden within database transactions.

## Consequences
- **Positive**: Eliminates deadlocks and race conditions during simultaneous user logins, identity linking, and unlinking.
- **Positive**: Deterministic token consumption guarantees single-use magic links.
- **Negative**: Advisory locking introduces small serialization pauses when identical credentials authenticate simultaneously.
